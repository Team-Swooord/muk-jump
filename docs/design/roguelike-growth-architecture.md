# 먹점프 로그라이크 성장·도감 아키텍처

> 문서 상태: 구현 기준안  
> 조사 기준일: 2026-07-29  
> 적용 범위: 메인 메뉴, 영구 성장, 한 판 성장, 성장 도감, 100개 성장 카탈로그

## 1. 목표

먹점프의 로그라이크 성장은 단순한 능력치 증가 화면이 아니라, 한 판마다
`어떤 방식으로 발판을 만들고, 점프를 유도하고, 분신을 살릴 것인가`를 바꾸는
선택 시스템이어야 한다.

핵심 목표는 다음과 같다.

1. 세로형 모바일 캐주얼 게임에서 한눈에 읽히는 최대 3개의 선택지만 제공한다.
2. 100개의 성장을 추가해도 필요한 조합이 나오지 않는 풀 오염을 막는다.
3. 영구 성장은 새 선택과 선택 제어권을 열고, 한 판 성장은 실제 플레이 방식을 바꾼다.
4. 기존 자동 점프·드로잉 발판·먹 자원·먹분신·바람·장애물 규칙을 파괴하지 않는다.
5. 도감이 외부 공략 없이 선행조건·상충 관계·완성 경로를 이해하게 한다.
6. Unity 모바일 환경에서 성장 수가 늘어도 프레임, GC, 오브젝트 수가 비례해 증가하지 않는다.
7. 새 성장 추가는 데이터와 효과 핸들러 추가로 끝나고, 로비·도감·선택 UI를 각각
   수정하지 않게 한다.

### 비목표

- 최고 점수 계산법을 고도 이외의 값으로 바꾸지 않는다.
- 영구 성장만으로 코어 플레이를 건너뛸 정도의 직접 전투력은 제공하지 않는다.
- Survivor.io식 다중 파편·장비·승급 통화를 여러 겹 추가하지 않는다.
- 100개를 처음부터 모두 활성화하지 않는다.
- 다른 게임의 명칭·아이콘·수치를 그대로 복제하지 않는다.

## 3. 먹점프의 100개 성장 구조

### 3.1 25계보 × 4노드

100개를 하나의 평면 목록으로 만들지 않는다. 다음 구조의 **25개 성장 계보**로 묶는다.

```text
계보 뿌리 1개
├─ 갈래 A 1개
├─ 갈래 B 1개
└─ 완성 1개

25계보 × 4노드 = 100개 성장 정의
```

- **뿌리**: 계보의 기본 동작을 연다. 주로 Common이며 여러 단계 강화가 가능하다.
- **갈래 A/B**: 같은 뿌리를 서로 다른 플레이 방식으로 바꾼다. 주로 Rare다.
- **완성**: 뿌리와 선택한 갈래를 결합해 플레이 규칙을 바꾸는 단발성 완성 효과다.
  Epic 또는 Legendary만 사용한다.
- 기본 규칙은 A/B 상호 배타다. 양쪽 동시 획득이 의도된 예외만 카탈로그의
  `branchMode`로 명시한다.
- 뿌리를 얻기 전에는 해당 갈래와 완성이 추첨 풀에 들어오지 않는다.
- 완성은 기본적으로 `뿌리 Lv.2 이상 + 갈래 하나 보유`를 요구하되, 실제 요구조건은
  코드 카탈로그에 기록한다.

계보는 다음 플레이 영역에 배분한다. 이 표는 콘텐츠 예산이지 100개 개별 정의 목록이 아니다.

| 영역 | 계보 수 | 담당 경험 |
|---|---:|---|
| 몸·생존 | 4 | 완충, 보호, 피격 후 대응, 마지막 생존 |
| 도약·궤적 | 4 | 점프 세기, 방향, 정점, 착지 |
| 먹·붓 자원 | 4 | 용량, 회복, 초과 먹, 획 비용 |
| 획·발판 | 5 | 수명, 동시 수, 형태, 낙묵석 대응, 특수 발판 |
| 먹분신 | 3 | 배치, 생존 공유, 분신 간 역할 |
| 바람·맵 | 3 | 횡풍, 상승기류, 구간 조건 활용 |
| 운·위험 거래 | 2 | 아이템 발견, 보상과 위험 교환 |
| **합계** | **25** | **100개 성장 정의** |

기존 `먹두께`, `도약`, `큰 벼루`, `먹샘`, `긴 여운`, `겹친 획`, `굳은 획`,
`길운`은 첫 계보들의 뿌리 또는 갈래 후보로 이관한다. 기존 효과 수치를 바로 폐기하지
않고 새 카탈로그에서 같은 런타임 계약을 통해 읽도록 옮긴다.

### 3.2 단일 진실 원천

**100개 개별 항목의 이름·설명·등급·단계·수치·아이콘·선행조건·상충 관계·해금 조건은
코드의 성장 카탈로그를 유일한 단일 진실 원천으로 사용한다.**

- 이 문서, README, 씬 빌더, 도감 프리팹에 100개 목록을 복사하지 않는다.
- 선택 UI, 성장 메뉴, 도감, 디버그 패널, 밸런스 시뮬레이터, 저장 마이그레이션은
  모두 같은 카탈로그를 조회한다.
- UI 문구를 별도의 `switch`로 다시 작성하지 않는다.
- 개별 성장 변경은 카탈로그 정의 한 곳과 필요 시 효과 핸들러 한 곳만 수정한다.
- 문서는 구조·규칙·품질 기준만 유지한다.

권장 정의 형태:

```csharp
GrowthDefinition
{
    Id;
    FamilyId;
    Category;
    Tier;
    Rarity;
    MaxRank;
    Weight;
    UnlockId;
    PrerequisiteIds;
    ExclusionIds;
    Tags;
    IconKey;
    EffectId;
    RankValues;
}
```

실제 타입 이름과 직렬화 방식은 현재 어셈블리 경계에 맞추되, 런타임에서 정의를
수정하지 않는 불변 카탈로그로 만든다.

## 4. 3지선다 추첨 규칙

### 4.1 역할 슬롯

매 선택창은 단순히 전체 후보에서 세 번 뽑지 않고 다음 역할을 하나씩 담당한다.

1. **이어가기**: 보유 계보의 다음 단계 또는 랭크 강화
2. **새 길**: 아직 보유하지 않은 계보의 뿌리
3. **변수**: 조건부 갈래·완성·희귀 카드 또는 전체 후보 중 시너지 카드

역할 후보가 비었을 때만 다른 역할의 남은 후보로 채운다. 최종 카드끼리는 항상
서로 다른 `GrowthId`여야 한다. 후보가 1~2개뿐이면 복제하지 않고 중앙 정렬한다.

### 4.2 후보 생성 파이프라인

```text
전체 코드 카탈로그
→ 계정에서 해금된 정의
→ 현재 런 모드·구간에 허용된 정의
→ 선행조건 충족
→ 상충 정의 제거
→ 최대 단계 제거
→ 역할 슬롯 분류
→ 보유 태그·현재 구간·희귀도 가중
→ 성장 전용 결정론 난수로 최대 3개 추첨
```

- 성장 난수는 아이템·장애물·날씨·연출 난수와 독립한다.
- 같은 시드와 같은 선택 이력은 같은 제안을 만들어야 한다.
- 리롤 직전 세 장은 바로 다음 결과에서 제외한다. 후보 부족 시에만 다시 허용한다.
- 새 계보만 계속 제시해 기존 계보를 완성하지 못하는 상황과, 보유 계보만 제시해
  새 빌드를 시작할 수 없는 상황을 모두 방지한다.
- 동일 계보가 세 칸을 모두 차지하지 않도록 기본 상한을 2칸으로 둔다.

### 4.3 등장 횟수 목표

한 번의 평균적인 유효 런에서 다음 경험을 목표로 한다.

- 성장 결정 8~12회
- 뿌리 계보 3~5개
- 완성 계보 1~2개
- 첫 두 선택에서는 최소 한 개의 새 뿌리 보장
- 첫 완성 후보는 선행조건을 만족한 뒤 지나치게 오래 기다리지 않도록 3회 이내에
  한 번 보장하는 완성 후보 천장 적용

현재 `45m 이후 120m 간격`이 실제 사용자 런에서 4회 이하의 선택만 만든다면,
간격을 임의로 바로 바꾸지 말고 테스트 로그를 바탕으로 60~80m 범위를 비교한다.
목표는 선택 수이지 특정 간격 숫자 자체가 아니다.

## 5. 해금·선행·상충·희귀도

### 5.1 해금

- 첫 실행에는 6~8개 계보만 연다. 기존 8종 성장이 이 시작 경험을 구성한다.
- 나머지는 최고 고도, 특정 장애물 방어, 바람 활용, 분신 생존, 특정 계보 완성과 같은
  **플레이 행동 업적**으로 해금한다.
- 해금은 선택지를 넓히는 수평 진행이 기본이다.
- 아직 해금하지 않은 도감 항목은 실루엣과 짧은 힌트를 보여주되 정확한 수치는 숨긴다.
- 해금 조건을 달성한 뒤에는 결과 화면과 로비에서 한 번씩만 신규 알림을 표시한다.

### 5.2 선행조건

- 갈래는 같은 계보의 뿌리를 요구한다.
- 완성은 뿌리와 갈래 또는 명시된 다른 계보 조합을 요구한다.
- 조건을 만족하지 않은 카드는 희귀도 추첨 전에 제거한다.
- 카드와 도감에는 `필요: 큰 벼루 Lv.2`처럼 사람이 이해할 수 있는 조건을 표시한다.
- 순환 선행조건과 자기 자신 요구조건은 에디터 검증에서 실패시킨다.

### 5.3 상충 관계

- 같은 계보의 A/B 갈래는 기본적으로 서로 상충한다.
- 물리 규칙을 서로 덮어쓰는 성장도 명시적 상충으로 정의한다.
- 상충 항목을 고르면 반대 항목은 해당 런의 후보에서 즉시 제거한다.
- 영구 봉인과 런 상충을 같은 상태로 저장하지 않는다.
- 상충 이유는 도감에 공개해 선택이 사라진 이유를 알 수 있게 한다.

### 5.4 희귀도

희귀도는 카드의 절대 우열보다 **복잡도와 규칙 변화의 크기**를 나타낸다.

| 희귀도 | 주 역할 | 기본 등장 조건 |
|---|---|---|
| Common | 뿌리·기본 수치·회복 | 시작부터 |
| Rare | 갈래·조건부 시너지 | 관련 뿌리 보유 또는 중반 높이 |
| Epic | 강한 조합·규칙 변경 | 선행 조합과 후반 높이 |
| Legendary | 계보 완성·단발성 변형 | 완성 조건 충족 + 별도 천장 |
| Cursed | 강한 보상과 명확한 손해 | 별도 위험 두루마리에서만 |

- 첫 선택에서 Epic·Legendary를 운으로 바로 얻지 않는다.
- 높이만으로 해금하지 않고 선택 횟수와 선행조건을 함께 본다.
- 희귀도 색만으로 정보를 전달하지 않는다. 테두리 붓결, 카드 상단 명칭, 문양 형태를
  함께 사용한다.

### 5.5 리롤·버리기·봉인

- **리롤**: 현재 세 장만 다시 뽑는다. 처음에는 없으며 영구 성장으로 1회부터 연다.
- **버리기(Banish)**: 현재 카드 하나를 이번 런의 후보에서 제거한다. 후반 해금으로 둔다.
- **봉인(Seal)**: 도감에서 선택한 항목을 다음 런부터 후보에서 제외한다.
- 봉인 슬롯은 처음 0개, 초기 구현 최대 3개로 시작하고 풀 규모와 테스트 결과에 따라 늘린다.
- 계보 뿌리를 봉인하면 그 뿌리에만 의존하는 갈래와 완성도 함께 비활성화된다고
  도감에서 미리 알려준다.
- 모든 해금 항목을 봉인해 선택 불능이 되지 않도록 최소 활성 계보 수를 강제한다.
- 리롤·버리기·봉인은 점수를 직접 올리지 않고 RNG 통제권만 제공한다.

## 6. 영구 성장과 한 판 성장 분리

### 6.1 영구 성장

로비의 `성장` 팝업에서 관리하며 저장 데이터에 남는다.

- 현재 1차 구현은 `먹빛` 한 종류만 사용하며 먹그릇(기본 최대 먹 +1.5%/Lv),
  숨고르기(기본 먹 회복 +2%/Lv), 먹결(기본 발판 수명 +1.25%/Lv),
  발놀림(자동 점프 충전시간 -0.75%/Lv)의 네 축을 각 6단계 제공한다.
- 정상 게임오버만 먹빛을 지급한다. 디버그·중도 포기는 0이며, 저장된 run ID로
  재정산을 차단한다. 첫 정상 종료에는 첫 구매 비용 6을 보장한다.
- 분신·부활·방패·아이템 빈도·점수 배율처럼 핵심 위험을 건너뛰는 영구 효과는
  제공하지 않는다.
- 리롤·버리기·봉인과 새 계보 해금은 카탈로그가 실제 런타임으로 확장된 뒤의
  후속 단계이며 현재 영구 화면에는 노출하지 않는다.

영구 순수 능력치의 합산 체감은 초기 기준 10~15% 이내로 제한한다. 영구 성장
비용을 모두 지불한 뒤에는 더 이상 먹빛이 생성되지 않도록 보유량+누적 소비량을
카탈로그 총비용 이하로 제한한다. 밸런스 버전이 바뀌면 소비분을 먹빛으로 돌리고
영구 단계만 초기화하며 최고 고도와 두루마리 도감은 보존한다.

### 6.2 한 판 성장

`RunGrowthState`에만 존재하며 새 도전에서 반드시 초기화한다.

- 현재 획득 성장과 랭크
- 선택한 갈래와 상충 잠금
- 이번 런의 버리기 목록
- 리롤 잔여 횟수
- 파생된 먹·점프·발판·분신·바람 배율

한 판 성장은 저장된 기본 Inspector 값을 직접 덮어쓰지 않는다. 각 시스템은
조회형 배율 또는 명시적 이벤트 효과를 받아야 하며, 재도전·로비 복귀·스크립트
재컴파일 후에도 중첩이 남지 않아야 한다.

### 6.3 통화

- 영구 성장 통화는 한 종류만 사용한다.
- 한 판 성장에는 별도 소모 통화를 요구하지 않고 성장 두루마리 획득 자체가 선택권이다.
- 여러 파편·등급 재료·확률 합성은 도입하지 않는다.
- 통화 수급량은 최고 고도만을 점수로 쓰는 규칙과 분리한다.

## 7. 런타임 아키텍처

권장 책임 경계:

| 구성 요소 | 책임 | 금지 사항 |
|---|---|---|
| `GrowthCatalog` | 100개 불변 정의와 유효성 검사 | 런 상태 저장, UI 오브젝트 참조 |
| `PermanentGrowthCatalog` | 영구 4축 stable ID·비용·상한·효과 | 런 두루마리 정의 |
| `PermanentGrowthProfile` | 먹빛·영구 단계·정산 run ID의 버전 저장 | 한 판 단계 저장 |
| `GrowthDraftService` | 후보 필터, 역할 슬롯, 가중치, 리롤 | 전역 `Random` 사용, UI 생성 |
| `RunGrowthState` | 현재 런의 랭크·갈래·상충·잔여 횟수 | 영구 저장 직접 쓰기 |
| `GrowthEffectRegistry` | `EffectId`를 작은 효과 핸들러로 연결 | 100개짜리 단일 거대 `switch` |
| `GrowthChoiceView` | 최대 3장의 표시와 입력 | 성장 규칙 재계산 |
| `GrowthCompendiumView` | 카탈로그·해금 상태를 읽어 도감 표시 | 별도 설명 데이터 보유 |
| `GrowthTelemetry` | 제안·선택·완성·사망 원인 기록 | 게임 결과에 영향 |

흐름:

```text
성장 두루마리 획득
→ GameManager가 성장 선택 일시정지 사유 획득
→ GrowthDraftService가 최대 3개 제안
→ GrowthChoiceView는 정의를 그대로 표시
→ 선택 검증
→ RunGrowthState 갱신
→ GrowthEffectRegistry가 해당 효과 적용
→ 일시정지 사유 반환
→ 플레이 재개
```

- 선택 팝업과 일반 일시정지 팝업이 동시에 열리지 않는 기존 계약을 유지한다.
- 효과 핸들러는 `PlayerController`, `StrokeCapture`, `PlatformCollider`,
  `ItemSpawner`의 소유 상태를 직접 빼앗지 않는다.
- 지속 수치 효과는 각 소유 시스템이 `RunGrowthState`의 읽기 전용 파생값을 조회한다.
- 일회성 효과만 이벤트로 전달한다.
- 씬 참조와 UI 생성은 `MukJumpSceneBuilder`에서 재현 가능하게 구성한다.

## 8. 메인 메뉴와 도감 UX

### 8.1 메인 메뉴 위계

세로 화면의 첫 메뉴는 다음 순서만 강하게 노출한다.

1. 제목 `먹점프`
2. 가장 큰 기본 행동 버튼 `시작`
3. 보조 버튼 `성장`
4. 보조 버튼 `도감`
5. 작은 설정·출처 버튼

- 기존의 시작 안내 문구를 실제 `시작` 버튼으로 바꾸고, 버튼을 누를 때만 플레이를 시작한다.
- `성장`과 `도감`은 `시작`보다 작고 같은 위계로 둔다.
- 최고 고도 정보는 시작 버튼과 경쟁하지 않는 한 줄 요약으로 둔다.
- 첫 화면에 통화, 알림, 도감 진행률을 여러 배지로 흩뿌리지 않는다.

### 8.2 영구 성장 전용 화면

게임 시작 전 로비에서 붓 전환으로 이동하는 불투명 한지 전용 화면에 보유 먹빛과
4축×6단계 먹나무 계보를 표시한다. 각 가지 카드는 현재 단계, 다음 효과, 비용,
최대 단계를 한 번에 보여주며 구매 즉시 저장한다.
리롤·버리기·봉인과 100종 계보는 현재 구현에 섞지 않고 `도감`과 후속 단계로 남긴다.

### 8.3 도감 전용 화면

- 현재 모바일 구현은 큰 그림 카드 4개를 2×2로 재사용하고, 탭하면 설명 뒷면으로
  뒤집는다. 100개 GameObject를 동시에 만들지 않는다.
- 필터: 전체, 몸, 도약, 먹·붓, 획·발판, 분신, 바람·맵, 운·위험.
- 정렬: 계보, 발견 순서, 희귀도, 미완성 우선.
- 발견 전: 회색 먹 실루엣, 해금 힌트, 계보 위치만 표시.
- 해금 후 미획득: 이름·기본 설명·첫 단계만 표시.
- 획득 후: 모든 랭크, 선행조건, 상충 관계, 완성 연결선, 최고 도달 단계 표시.
- 현재 런에서는 보유·최대 단계·상충 잠금 상태를 겹쳐 표시한다.
- 신규 표시는 작은 검은 붓결 또는 절제된 금빛 매듭으로 한 번만 표시한다.
- 검색어나 수치가 없어도 아이콘과 계보 연결만으로 관계를 파악할 수 있게 한다.
- 5열 가상화 그리드와 별도 상세 패널은 태블릿·가로 화면을 검토할 때의 후속안이며
  현재 세로 모바일 화면의 기준이 아니다.

### 8.4 한국 수묵 시각 규칙

- 한지, 먹 번짐, 갈필, 매듭, 구름, 붓획, 두루마리 모티프를 사용한다.
- 일본식 일장기처럼 읽힐 수 있는 중앙 붉은 원, 반복 붉은 점, 무의미한 낙관 장식을 금지한다.
- **빨강은 실제 위험, 저주, 최고 기록 낙관처럼 의미가 있을 때만 사용한다.**
- 일반 신규 알림, 희귀도, 선택 강조에 빨간 점을 사용하지 않는다.
- 아이콘은 텍스트·수치·카드 프레임 없는 투명 단일 심벌로 제작해 도감·카드·디버그에서
  재사용한다.
- 희귀도는 빨간 점 대신 먹선 수, 테두리 붓결, 한지 명도, 금빛의 제한적 사용으로 구분한다.

## 9. 모바일 성능 기준

성장 항목 수가 8개에서 100개로 늘어도 활성 오브젝트와 매 프레임 비용은 늘지 않아야 한다.

- 각 성장마다 `GameObject`, `MonoBehaviour`, `Update()`를 만들지 않는다.
- 지속 수치는 `RunGrowthState`에서 한 번 집계하고 변경 시에만 다시 계산한다.
- 제안 생성 시 LINQ, 반복 문자열 조합, 임시 리스트 할당을 피하고 재사용 버퍼를 쓴다.
- 선택 UI는 카드 3개를 고정 생성해 내용만 교체한다.
- 도감 셀은 가상화 또는 페이지 단위 재사용을 적용해 100개 전체 오브젝트를 동시에
  활성화하지 않는다.
- 아이콘은 동일 임포트 규칙과 아틀라스 사용을 검토하고, 100번의 런타임
  `Resources.Load` 탐색을 하지 않는다.
- 성장 VFX는 `docs/VFX/SKILL.md`의 Low·Medium·High 예산과 기존 풀을 사용한다.
- Proc, 분신, 낙묵석, 파티클이 서로 재귀적으로 발동하지 않도록 한 프레임·한 대상
  발동 상한을 둔다.
- 분신 수, 발판 수, 사망 자국, 바람선의 기존 풀 상한은 성장으로 무제한 해제하지 않는다.
- Low 품질에서도 위험 경고·방어 성공·마지막 생존 사망은 생략하지 않는다.
- 성장 선택을 여닫을 때 `Time.timeScale`과 오디오가 기존 일시정지 소유권을 침범하지 않는다.

## 10. 풀 오염 방지

100개 카탈로그와 현재 추첨 풀은 같은 뜻이 아니다.

- 처음에는 6~8개 계보만 해금한다.
- 선행조건을 충족하지 않은 2·3단계 노드는 후보에 존재하지 않는다.
- 최대 단계, 상충, 봉인 항목은 가중치 계산 전에 제거한다.
- 보유 태그와 계보에 적당한 가중치를 주되 새 계보 역할 슬롯은 항상 남긴다.
- 새 콘텐츠를 추가할 때 같은 수만큼 봉인 슬롯을 무조건 늘리기보다,
  실제 후보 크기·완성률·리롤 사용률을 보고 조정한다.
- 선택되지 않는 약한 카드를 단순 상향만 하지 말고 역할 중복, 선행 위치, 설명 가독성을
  함께 검토한다.
- 일반 수치 카드가 전체의 대부분을 차지하지 않게 하고, 각 계보 완성은 눈에 보이는
  플레이 변화 하나를 반드시 만든다.

## 11. 밸런스와 자동 검증

### 11.1 결정론 테스트

- 같은 시드·같은 상태는 같은 세 장을 반환한다.
- 아이템·장애물 난수 호출 횟수가 성장 제안으로 변하지 않는다.
- 제안 안에 같은 `GrowthId`가 중복되지 않는다.
- 최대 단계·미해금·상충·봉인·선행 미충족 항목은 나오지 않는다.
- 모든 역할 후보가 비었을 때도 유효한 폴백 또는 명시적 종료 보상을 반환한다.
- 계보 선행 그래프에 순환이 없다.
- 모든 `EffectId`, `IconKey`, 현지화 키가 유효하다.
- 저장 파일에 삭제된 성장 ID가 있어도 안전하게 무시하거나 마이그레이션한다.

### 11.2 시뮬레이션

최소 다음 시나리오를 10,000개 이상의 고정 시드로 반복한다.

1. 기본 해금 상태
2. 100개 전체 해금
3. 봉인 슬롯 최대 사용
4. 특정 계보 한 개 집중
5. 여러 계보 분산
6. 모든 일반 항목 최대 단계 근접
7. 리롤·버리기 반복
8. 24분신·강풍·낙묵석·먹비가 겹치는 성능 상한

수집 지표:

- 제안 횟수와 선택 횟수
- 항목별 제안률·선택률·리롤률
- 계보 뿌리→갈래→완성 전환률
- 첫 완성까지 필요한 선택 수·고도
- 무효 또는 0개 선택창 발생률
- 완성 계보별 최고 고도·사망 원인
- 리롤·봉인 유무에 따른 빌드 완성률
- 분신 수·발판 활성 수·VFX 활성 수·GC Alloc·프레임 시간

초기 가설:

- 평균 유효 런의 성장 선택 8~12회
- 완성 계보 1~2개
- 0개 선택창 0%
- 같은 카드 중복 제안 0%
- 특정 필수 카드의 선택률이 과도하게 높으면 효과뿐 아니라 대안 품질을 재검토
- 전체 해금이 기본 해금보다 평균 완성률을 크게 낮추면 태그 가중·봉인·역할 슬롯을 조정

이 수치는 출시 확정값이 아니라 실제 테스트 로그로 보정할 기준이다.

### 11.3 플레이 테스트 질문

- 세 장을 3초 안에 대략 이해할 수 있는가?
- 왜 갈래나 완성이 나타났는지 설명할 수 있는가?
- 선택 직후 플레이 변화가 보이는가?
- 공격적 선택과 생존 선택 모두 최고 기록 가능성이 있는가?
- 특정 카드가 나오지 않으면 런을 포기하고 싶은가?
- 영구 성장을 초기화해도 게임이 온전히 플레이 가능한가?
- 도감만 보고 완성 조건을 이해할 수 있는가?
- 100개를 모두 해금한 계정에서도 원하는 계보를 실제로 완성할 수 있는가?

## 12. 단계별 구현 로드맵

### 0단계 — 계약과 카탈로그 기반

- 불변 `GrowthCatalog`와 정의 검증기
- `GrowthDraftService`, `RunGrowthState`, `GrowthEffectRegistry` 인터페이스
- 성장 전용 난수 스트림과 결정론 테스트
- 기존 8종을 새 정의로 읽는 호환 어댑터

완료 조건: UI 없이 테스트에서 기존 8종 선택과 효과가 동일하게 동작한다.

### 1단계 — 메인 메뉴·성장·도감 골격

- 명시적 `시작` 버튼
- 메인 메뉴 `성장`, `도감` 진입
- 성장 팝업 3탭 골격
- 100개를 읽을 수 있는 가상화 도감 그리드
- 미발견·해금·획득·최대 단계 상태

완료 조건: 임시 아이콘으로도 코드 카탈로그 변경이 메뉴와 도감에 자동 반영된다.

### 2단계 — 기존 8종 이관

- 기존 8종의 단계·효과·세션 초기화를 새 런 상태로 이전
- 역할별 3지선다
- 리롤 1회 개발용 기능
- 씬 빌더와 디버그 패널 연결

완료 조건: 기존 회귀 테스트와 새 추첨 테스트를 모두 통과하고 플레이 감각이 악화되지 않는다.

### 3단계 — 첫 6계보, 24개 성장

- 6계보의 뿌리·갈래·완성 구현
- 첫 해금 흐름과 도감 힌트
- 계보 완성 전용 두루마리 연출
- 영구 성장 통화 한 종류와 환불

완료 조건: 평균 런에서 최소 한 계보를 완성하고 서로 다른 빌드 3개가 성립한다.

### 4단계 — 15계보, 60개 성장

- 분신·바람·장애물 조건부 계보 확장
- 상충 관계와 버리기
- 도감 필터·연결선·현재 런 상태
- 10,000시드 풀 오염 시뮬레이션

완료 조건: 전체 해금 상태에서도 무효 선택 없이 계보 완성률 목표를 충족한다.

### 5단계 — 25계보, 100개 성장

- 나머지 계보와 위험 거래 두루마리
- 봉인 시스템
- 모든 아이콘을 범용 투명 심벌로 교체
- 저장 버전과 카탈로그 마이그레이션
- 신규 항목 알림과 결과 요약

완료 조건: 코드 카탈로그 100개 유효성 검사, 모든 효과 핸들러·아이콘·설명 연결,
100개 전체 해금 시뮬레이션을 통과한다.

### 6단계 — 밸런스·모바일 제출 검증

- 실제 플레이 로그와 선택 퍼널 분석
- 저사양 Android의 24분신·VFX 최악 조합 프로파일링
- 선택 빈도·희귀도·천장·봉인 슬롯 조정
- 한국어 가독성, 터치 영역, 뒤로가기, 앱 일시정지·복귀 검증
- 도감과 AI 활용 문서의 최종 출처·이미지 라이선스 확인

완료 조건: 코어 루프 회귀, EditMode·PlayMode, Android 실기기 장시간 테스트를 통과한다.

## 13. 반드시 피할 함정

1. 100개를 균등한 단일 풀로 활성화해 필요한 조합이 나오지 않는 문제
2. 새 해금이 늘수록 플레이어가 약해지는 풀 오염
3. 이름만 다른 `+5%`, `+7%`, `+9%` 카드 양산
4. 영구 성장으로 첫 플레이와 숙련 플레이의 난이도가 완전히 달라지는 문제
5. 선행조건을 숨겨 외부 위키 암기를 강요하는 UX
6. 저주 카드와 일반 카드를 같은 모양으로 제시해 오선택을 유도하는 UX
7. 선택 팝업이 너무 자주 열려 드로잉 흐름을 끊는 문제
8. Proc·분신·파티클 연쇄를 무제한 허용해 모바일 프레임이 무너지는 문제
9. 여러 통화·파편·합성·등급 시스템을 동시에 도입하는 메타 과부하
10. 카탈로그와 UI·도감의 별도 목록이 어긋나는 데이터 중복
11. 성장 효과가 Inspector 기본값을 직접 바꿔 재도전에서 중첩되는 문제
12. 장식용 빨간 점과 중앙 붉은 원을 반복해 한국 수묵 정체성을 흐리는 문제

## 14. 최종 원칙

먹점프의 100개 성장은 **100개의 독립 카드**가 아니라 **25개의 이해 가능한 성장 이야기**다.
플레이어는 매번 세 장만 보지만, 보유 계보와 행동에 따라 다음 선택의 의미가 달라져야 한다.

코드는 카탈로그 하나를 단일 진실 원천으로 삼고, 런 상태·영구 상태·효과 적용·UI를
서로 분리한다. 아트는 한지와 먹의 절제를 유지하며, 빨강은 실제 의미가 있을 때만 쓴다.
이 원칙을 지키면 콘텐츠가 8개에서 100개로 늘어도 선택은 읽기 쉽고, 빌드는 완성 가능하며,
모바일 성능과 제출용 코드 품질을 함께 유지할 수 있다.
