# 영구 성장 39열매 밸런스 v2

> 기준일: 2026-08-01
> 상태: 구현 전 기획 기준안
> 범위: 로비 영구 성장만 해당. 한 판 전용 `증강`과 월드 아이템은 변경하지 않는다.

## 1. 확정 원칙

1. 모든 열매는 예외 없이 **성장 먹물방울 1개**로 한 번만 해금한다.
2. 총 39개 열매는 `생존 8 / 도약 12 / 먹 운용 19`로 유지한다.
3. 각 열매는 고유 이름과 고유 아이콘 파일을 가진다. 같은 계열은 중심 상징과
   붓 방향을 공유하되 외곽 윤곽을 조금씩 바꾼다.
4. 작은 수치 열매를 따라간 뒤 각 계보의 마지막 열매에서 규칙형 패시브 하나를 연다.
5. 점수 배율, 시작 분신, 일반 아이템 확률은 영구 성장에 넣지 않는다.
6. 빨강은 해금된 열매 상태, 금빛은 선택·최종 패시브 상태를 UI가 담당한다.
   아이콘 원본에는 빨강·금빛·숫자·레벨 점을 넣지 않는다.

월드에서 먹으면 50m 상승하는 `먹물방울`과 혼동하지 않도록 성장 화면과 결과창에서는
재화를 **성장 먹물방울**이라고 표기한다. 저장 코드 내부 명칭은 기존 `Currency`를
유지해 다른 시스템과의 결합을 늘리지 않는다.

## 2. 획득 경제

### 2.1 지급 규칙

- 첫 정상 게임오버는 고도와 관계없이 성장 먹물방울 1개를 보장한다.
- 그다음부터 10m 이상 도달한 정상 게임오버마다 1개를 지급한다.
- 최고 기록이 처음으로 `100 / 250 / 500 / 750 / 1000m`를 넘을 때마다 해당
  이정표 보너스 1개를 추가한다. 한 판에 여러 이정표를 넘으면 모두 합산한다.
- 첫 판 보장과 10m 기본 보상은 중복하지 않는다.
- 디버그 사용 판, 중도 포기, 이미 정산한 도전 ID는 0개다.
- 보유량과 이미 소비한 양의 합은 남은 열매 수를 넘지 않는다.

예시:

| 결과 | 지급 |
|---|---:|
| 첫 정상 판, 0m | 1 |
| 일반 판, 9m | 0 |
| 일반 판, 10~99m | 1 |
| 최고 80m에서 처음 120m | 2 = 기본 1 + 100m 1 |
| 최고 120m에서 처음 520m | 3 = 기본 1 + 250m 1 + 500m 1 |
| 최고 0m에서 처음 1000m | 6 = 기본 1 + 이정표 5 |

### 2.2 완성 속도 목표

- 이정표 보너스 다섯 개를 모두 받으면 정확히 **34번의 보상 판**으로 39개를 완성한다.
- 이정표를 받지 못하면 최대 39번의 보상 판이 필요하다.
- 문서상 한 판 1~3분 기준 약 34~117분의 장기 진행이다.
- 짧은 고의 추락을 막기 위해 첫 판 이후에는 10m 미만을 보상하지 않는다.

이 값은 실제 사용자 로그가 없는 상태의 목표치다. 출시 전에는 `고도 / 플레이 시간 /
사망 원인 / 지급량 / 구매 경로`를 익명 로컬 QA 표로 수집해 10m 기준만 재검토한다.

## 6. 39개 아이콘 제작 규격

- 파일: `Assets/Resources/MukJump/UI/PermanentGrowth/Icons/`
- 명명: 위 표의 `pg_icon_<family>_rNN.png`
- 크기: 투명 `256×256 PNG`, 실제 피사체 경계 `208~224px`
- 색: `INK #1C1B1A`와 옅은 먹 한 톤. 상태색은 넣지 않는다.
- 금지: 문자, 숫자, `+`, 레벨 점, 흰 외곽선, 그림자, 빨강, 금색, 재화 방울 장식
- 같은 계열은 먹 질감·무게중심·붓 진행 방향을 고정한다.
- 인접 단계는 미세한 노이즈가 아니라 **외곽 윤곽과 내부 큰 덩어리를 10~14%** 바꾼다.
  실제 540×960 화면에서 약 30px로 보이므로 작은 점 하나만 추가하는 방식은 금지한다.
- 각 파일은 서로 다른 실루엣이어야 하며 파일 해시 39개도 모두 달라야 한다.
- 노드의 빨간 열매, 잠금 먹원, 선택 금빛 고리는 현재 UI 계층에서 별도로 합성한다.

런타임은 `PermanentGrowthNodeDefinition`에 `DisplayName`과 `IconKey`를 두고
`Type + Rank`로 39개 파일을 조회한다. 기존 7개 공용 아이콘은 개발 중 누락
폴백으로만 남기며, 제출 빌드 검증에서는 폴백 사용을 실패로 처리한다.

## 7. 저장 마이그레이션

비용 배열만 1로 바꾸고 기존 `balanceVersion=1`을 유지하면 과거의 높은 `spent`가
환급되어 거의 모든 열매를 즉시 살 수 있다. 반대로 현재 공통 버전 마이그레이션을
그대로 사용하면 기존 해금 단계가 모두 초기화된다. 둘 다 허용하지 않는다.

`balanceVersion=2` 전용 변환은 다음 순서를 사용한다.

1. 기존 stable ID와 해금 레벨은 그대로 보존한다.
2. 새 `spent`는 저장된 레벨 합, 즉 이미 열린 열매 수로 다시 계산한다.
3. 구 지갑은 남은 구 비용 대비 진행 비율만 보존한다.
   `floor(구 wallet / 구 남은 비용 × 새 남은 열매 수)`로 변환한다.
4. 새 지갑은 `0..새 남은 열매 수`로 제한한다.
5. 최고 고도, 첫 보상 지급 여부, 마지막 정산 도전 ID는 유지한다.

구 경제 총비용은 957, 새 경제 총비용은 39다. 이 비례 변환은 이미 구매한 열매를
회수하지 않으면서도 과거 먹빛 수십 개가 새 열매 수십 개로 그대로 바뀌는 것을 막는다.

## 8. 적용 순서

1. 이 문서의 명칭·수치·선행 관계를 확정한다.
2. 카탈로그에 39개 표시명·아이콘 키와 전부 비용 1을 반영한다.
3. 보상식을 1개 기본 + 고정 이정표 보너스로 교체한다.
