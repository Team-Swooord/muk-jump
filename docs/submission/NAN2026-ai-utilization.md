# 먹점프를 만든 19일의 AI 활용 기록

## 프로젝트 정보

- 팀: 최연소밴드 — 김승연, 최성빈
- 개발: 2026.07.20–2026.08.07
- 프로젝트: Unity 6000.3.10f1 · 모바일 세로형 게임
- 개발 기록: 300개 이상의 기능 단위 커밋
- AI 활용 기록: 200건 이상의 작업 로그
- 증빙 원문: `docs/ai-usage-log.md`

먹점프는 기획 초안, 코드, 수묵 아트, 사운드, 밸런스, QA, 제출 문서까지 전 과정에서
AI를 사용했다. 그렇다고 한 번의 프롬프트로 게임을 만든 것은 아니다. 두 사람이 문제와
기준을 정하고, AI가 여러 대안을 내면 직접 플레이해 버릴 것과 남길 것을 골랐다.

완성된 답만 기록하지 않았다. 요구를 잘못 이해해 과하게 고친 사례, 구현했다가 게임의
중심을 흐려 삭제한 기능, 실기기에서 다시 발견한 UI 문제도 남겼다. 이 기록은 AI가
무엇을 생성했는지보다, 사람이 어떤 근거로 수정하고 거절했는지를 보여 준다.

## 실제 작업은 이렇게 반복됐다

1. **팀이 문제를 적었다.** 원하는 플레이 감각, 바꾸면 안 되는 규칙, 완료 조건을 먼저 정했다.
2. **AI가 대안을 냈다.** 코드 변경안, 수치 비교, 이미지 프롬프트, 실패 경로를 제안했다.
3. **사람이 골랐다.** 재미, 모바일 가독성, 수묵 스타일, 라이선스에 맞지 않는 결과를 버렸다.
4. **Unity에 연결했다.** 선택한 결과만 코드·에셋·씬 빌더에 통합했다.
5. **다시 깨뜨려 봤다.** 정적 컴파일, 회귀 테스트, Game View, iPhone 실기기로 확인했다.
6. **결정을 남겼다.** 채택·폐기 이유를 AI 로그와 기능 단위 커밋에 기록했다.

AI는 초안과 비교안을 빠르게 만드는 데 강했다. 사람은 화면에서 읽히는지, 점프가
재미있는지, 저장이 안전한지, 게임의 범위를 어디서 멈출지를 결정했다.

## 사례 1 — 먹 게이지의 뜻을 다시 정했다

초기 먹 게이지는 시간이 지나면 차는 일반적인 에너지 바에 가까웠다. 플레이가 길어지자
발판이 너무 많이 쌓였고, 화면 가장자리에서는 선을 이용한 벽타기가 가능해졌다.

팀은 게이지를 `시간을 기다리는 비용`이 아니라 `화면에 남길 수 있는 먹선 예산`으로
바꾸기로 했다. AI와 함께 총량 제한, 자연 건조, 오래된 획 우선 소멸을 비교했고,
다음 규칙만 남겼다.

- 기본 용량은 4.8m.
- 새 획을 그리면 가장 오래된 선의 시작점부터 사라진다.
- 붓자국과 물리 충돌 판정이 같은 비율로 줄어든다.
- 사라진 길이만큼 하단 게이지가 다시 찬다.

연속 획이 최대 길이에서 두 번 생성되는 문제, 프레임 경계를 넘긴 꼬리가 사라지는 문제,
먹 소모 할인이 실제 그리기 길이에 반영되지 않는 문제도 코드 감사에서 발견해 회귀
테스트로 남겼다. 규칙을 바꾼 뒤 UI·물리·성장 수치까지 함께 고쳤다.

## 사례 2 — 생성 이미지를 게임 자산으로 만들었다

캐릭터와 아이템을 만들 때 `검정과 한지색 중심, 굵은 먹 외곽선, 단순하고 귀엽게,
텍스트와 3D 표현 없음`처럼 눈에 보이는 제약을 먼저 적었다. 초안은 ChatGPT와
OpenAI ImageGen으로 만들었고, 팀이 채택본을 골랐다.

처음 나온 아이템은 캐릭터보다 금속 질감이 강하고 세밀했다. 그대로 쓰지 않고 색을
줄이고 외곽선 두께를 맞췄다. 캐릭터, 먹물방울, 방어막, 황금 붓, 먹분신의 피사체 크기를
통일하고, 배경 제거·알파 보정·기준점 정규화를 거쳐 Unity 스프라이트로 만들었다.

용과 해태도 같은 방식으로 제작했다. 프롬프트로 네 프레임 동작을 얻은 뒤 프레임마다
달라진 몸통 크기와 여백을 다시 맞췄다. AI가 만든 이미지는 최종 에셋이 아니라
팀이 검수하고 다듬는 원재료였다.

## 사례 3 — 저장 실패를 먼저 상상했다

영구 성장에는 먹빛, 39개 노드, 활성 줄기, 누적 거리와 정산 이력이 저장된다. 정상
플레이만 확인하면 잘 보이지 않는 문제를 찾기 위해 구현 작업과 검수 작업을 나눴다.
검수 쪽에는 `데이터를 잃을 수 있는 순서를 끝까지 찾아라`고 지시했다.

그 과정에서 다음과 같은 실제 경계가 발견됐다.

- 손상된 JSON을 빈 정상 저장으로 덮어쓰는 경로.
- 새 저장은 성공했지만 백업 갱신 중 앱이 끝나는 경우.
- 미래 버전 저장을 구버전 코드가 조용히 잘라 내는 경우.
- 복구와 초기화 버튼을 빠르게 눌러 정상 저장까지 지우는 경우.
- 최고 기록과 먹빛 정산 중 하나만 저장되는 경우.

재현 가능한 보고만 코드로 고쳤고, 실패 주입용 저장소와 회귀 테스트를 추가했다.
손상·미래 버전 저장은 자동 초기화하지 않고 읽기 전용 복구 상태로 열며, 교체 전 원본은
격리 보관한다. AI의 역할은 많은 실패 조합을 제시하는 것이었고, 어느 경로가 실제
위험인지 판단하고 완료 조건을 정한 것은 팀이었다.

## 만들었다가 버린 것도 있다

플레이 중 무작위 증강 카드, 아이템 도감, 안전 휴식 발판을 구현한 적이 있다. 기능은
동작했지만 한 획을 그리고 오르는 핵심 리듬이 흐려졌다. 제출 일정 안에서 더 많은
콘텐츠를 남기는 대신 세 기능을 제거하고 영구 성장 세 계보에 집중했다.

모바일 UI도 시뮬레이터에서 맞는 것만으로 끝내지 않았다. iPhone 실기기에서 튜토리얼
문장이 카드 밖으로 나오고 붓과 버튼이 작아지는 장면을 확인한 뒤 Safe Area, 고정 글자
크기, 버튼 터치 영역을 다시 잡았다. AI의 제안이 빠르더라도 실제 화면이 기준이었다.

## 검증과 실행 독립성

- Unity Runtime·Editor 정적 컴파일과 기능별 회귀 테스트를 반복 실행했다.
- 씬은 Inspector에서 손으로 고치지 않고 `MukJumpSceneBuilder`로 재생성한다.
- 9:16, Android 20:9, iPhone 19.5:9 Safe Area 계약을 확인했다.
- 실제 화면 검수는 iPhone 실기기와 Android 세로 해상도 프리셋을 사용했다.
- 게임 규칙 난수와 연출 난수를 분리해 VFX 호출 순서가 난도를 바꾸지 않게 했다.

제출 빌드는 외부 AI API나 API 키를 사용하지 않는다. `SketchToInkService`와
`FallbackInkStyle`이 프로젝트 안에서 갈필 질감을 만든다. 계정 연동과 자체 원격 전송을
사용하지 않으며 UID·설정·기록은 기기 로컬에 저장한다.
